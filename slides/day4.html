Session 1

The model supply chain

  • Trace a model artefact to its source and revision
  • Hash every file and compare with the publisher's list

01
The model supply chain

A model is a folder of files from somewhere

Publishertrains and releases
→
Hub or mirrorstores and serves copies
→
Your registrywhat the pipeline pulls
→
Engineloads it for users

Each hop is a place where a file can be swapped: weights, tokenizer, configuration, even the licence.

Ask the room where their last model came from and whether anyone checked the bytes. Usually the answer is "from the hub, by name". A name is not an identity.

Where tampering hides

Every file in the folder changes behaviour, not only the weights

Weights

A changed shard plants a behaviour that only some inputs trigger.

Tokenizer and config

A changed vocabulary or setting silently changes every answer.

Loadable code

Pickled formats can run code when loaded; safetensors stores tensors only.

The stretch of Lab 4.1 asks which extensions an admission policy should refuse; Lab 4.3's gate refuses .bin, .pt, .pkl and .pickle.

Lab 4.1 · the finding

One shard of the mirrored copy is not what the publisher released

artefact   athar-small-v1-mirror
file       model-00002-of-00002.safetensors
expected   be1f25b1cc7b4c31...
found      eff1f6fb22ae544a...
decision   do not admit; obtain from the publisher and verify its signature

64 bytes of 24,576 differ. A hash proves the bytes differ, not who changed them or why.

The mirror's record lists the publisher's hashes, correctly: only hashing the received file shows the change. Ask: what if the mirror had changed the list too? That question is the next session.

What goes wrong

A hash list from the same place as the files proves nothing

  • Whoever can change a shard on a mirror can change the list beside it
  • The list must be signed by the publisher, and the key must reach you another way
  • Then a change to any file, or to the list, fails verification

This is the bridge to Session 2: a signed manifest of file hashes is exactly what OpenSSF Model Signing produces.

Checkpoint

The hashes match; is the model safe to admit?

Every file of a downloaded model matches the hash list published on the same mirror. What can you conclude?

The files are the publisher's originals
The files match that list, and nothing more until the list is verified
The model may be used commercially
The model will answer as well as the original
Why. A matching hash is only as trustworthy as the list; a list from the mirror can be changed with the files.

Answer: B.

Session 2

Signing and verification

  • Sign a model folder as a manifest of hashed files
  • Verify the signature at admission
  • Explain what a signature proves and what it does not
02
Model signing

Sign a manifest of every file's hash, not one archive

Hashevery file in the folder
→
Statementan in-toto list of files and digests
→
Signin a DSSE envelope
→
Bundlea Sigstore bundle beside the model

This is the format of OpenSSF Model Signing (the model_signing package, from the sigstore/model-transparency project): the signed statement lists each file with its digest under the predicate type https://model_signing/signature/v1.0. Large models hash in parallel, and verification names the file that changed.

Sources: sigstore/model-transparency README.

Two ways to sign

Sign with a key you guard, or keylessly with an identity

A key

An elliptic-curve key pair. Verification needs the public key from a trusted channel. The lab uses this: no account, no network.

Keyless (Sigstore)

A short-lived certificate for a sign-in identity, recorded in a public transparency log. Verification names the identity and its provider.

The model_signing tool also supports certificates and hardware keys through PKCS #11. For a government service, where the key lives (a hardware module, the cloud provider's key service) is a control the NCA Cloud Cybersecurity Controls care about: name it in the review.

Lab 4.2

Three lines sign; three lines verify

model_signing.signing.Config().use_elliptic_key_signer(
    private_key="key.priv").sign(model, "model.sig")

model_signing.verifying.Config().use_elliptic_key_verifier(
    public_key="key.pub").verify(model, "model.sig")   # raises on failure

The package used in the course's runs was model-signing 1.1.1 from PyPI; on Windows it also needed pyOpenSSL installed, which the lab environment includes. The same is available as a command: model_signing sign key and model_signing verify key.

Lab 4.2 · results

Change one character, or use another key, and verification fails

CheckResult
signed folder, signer's public keyverified
tokenizer.json with one number changedsignature mismatch: hash mismatch for tokenizer.json
original folder, a different public keykey mismatch

The error names the file: that is the value of a per-file manifest. Restore the file and it verifies again.

Limits

A signature proves who signed which bytes, nothing more

  • Proves: every file is what the key holder signed
  • Does not prove: that the model is good, safe or free of planted behaviour
  • Does not prove: that you may use it: licences are a separate rule

Where the key comes from

The pipeline holds the trusted public key. A key shipped beside the model can be replaced with the model.

Ask: which of Day 3's problems would a signature have caught? None: v2.4 was signed and broken. Integrity and quality are different gates.

Checkpoint

The signature verifies

A model folder and its signature bundle both came from a partner's file share, along with the public key to check them. The signature verifies. What has been shown?

The partner released these exact files
The model contains no planted behaviour
Only that the files match whoever holds that key, which could be anyone with access to the share
Rasael may deploy it in production
Why. The key travelled with the files; anyone who could replace the files could replace the key. Get the partner's key through a separate, trusted channel.

Answer: C.

Session 3

Bills of materials and admission

  • Write a CycloneDX ML-BOM for a model
  • Write an admission policy with logged reasons

03
Bills of materials

A machine learning bill of materials says what the release contains

"components": [{
  "type": "machine-learning-model", "name": "athar-small-v1",
  "publisher": "Rasael ML platform team",
  "licenses": [{"license": {"id": "Apache-2.0"}}],
  "modelCard": {"modelParameters": {"task": "text-generation"}},
  "components": [{"type": "file", "name": "model-00001-of-00002.safetensors",
                  "hashes": [{"alg": "SHA-256", "content": "750bb039..."}]}]
}]

CycloneDX supports machine learning models as a component type with a model card. The lab's BOM validates against the CycloneDX 1.7 schema with cyclonedx-python-lib; the current specification release is 1.7.2.

Sources: CycloneDX ML-BOM capability page; CycloneDX specification releases.

The admission gate

Four rules, all of which must pass, each logged with its reason

  1. The signature verifies with the release key the pipeline holds
  2. The bill of materials validates, and its hashes equal the signed digests
  3. The licence is on the allow list (Apache-2.0, MIT)
  4. No file format that runs code when loaded

The allow list is a decision for Rasael's legal and data governance owners, not for the engineer; the gate enforces what they decided. Ask the room what their allow list would contain.

In the cluster

The cluster refuses any pod the gate did not admit

validate:
  failureAction: Enforce
  pattern:
    metadata:
      annotations:
        models.rasael.example/signature: "verified"
        models.rasael.example/licence: "Apache-2.0 | MIT"

Kyverno is one example of an admission controller; current Kyverno documents failureAction per validate rule (the older spec.validationFailureAction is deprecated). The cluster trusts the gate's annotations: who may write them is itself a control to review.

Sources: Kyverno documentation, Validate Rules.

Data governance

The model's records are classified data too

  • Admission logs and BOMs name suppliers, versions and keys: classify them before sharing
  • Telemetry with answers can hold personal data: it inherits the answers' classification
  • Where the release key and the model store live is a cloud control to review

The NDMO Data Classification Policy defines four levels (Top Secret, Secret, Restricted, Public) by the impact of disclosure; the NCA Cloud Cybersecurity Controls apply to services hosted in the cloud. Name the classification of each artefact in the capstone review; do not quote clause numbers from memory.

Sources: NDMO Data Classification Policy; NCA Cloud Cybersecurity Controls.

Session 4

Production readiness reviews

  • Apply a readiness checklist to another team's evidence
  • Rank findings by likelihood and impact

04
Readiness reviews

A readiness review decides whether another team's service may launch

Evidence

Measured results, not claims: curves, logs, replays, drills.

Ranking

Findings ordered by risk to users and to the organisation.

Decision

Launch, launch with dated conditions, or not yet, and what would change it.

The SRE book describes production readiness reviews as the way an SRE team takes on a service: a structured review of its reliability before support is accepted. SDAIA's National AI Risk Management Framework offers a method to identify, assess, treat and monitor AI risks; a readiness review is where those meet a launch date.

Sources: Google SRE book, The Evolving SRE Engagement Model; SDAIA, National AI Risk Management Framework (executive summary).

The checklist

Thirteen items in six areas: this week, as questions

AreaThe question
ObjectivesPer language, with burn-rate alerts?
CapacityLoad-tested to the busiest hour, with admission limits?
DegradationModes tested under faults, and disclosed?
IncidentsRoles, a decision log, the breach procedure?
ReleaseA canary with a quality gate; a tested rollback?
IntegrityA verified signature and a bill of materials?

Each area maps to a day of the course: the checklist is the course turned around and pointed at another team.

Lab 4.4 · ranked

Risk = likelihood × impact × gap; the top three decide the review

FindingStatusRisk
Load test only at the average hour (2.1 a second; the busiest was 6.4)missing16
Weights from a third-party mirror, unsignedmissing15
Quality objective on English samples onlypartial10
Runbook without roles or a decision logmissing9
Quality alert on a daily averagepartial8

The gap is 1 for missing and 0.5 for partial; likelihood and impact come from Rasael's checklist. The ranking is a starting point for judgement, not a replacement for it: participants may argue an order, with reasons.

The decision

Not yet: an unsigned model blocks the launch

Blocking

Missing with impact 5: the model signature. Nobody can show the weights are the publisher's, and Lab 4.1 found a tampered mirror.

Conditions

Busiest-hour load test and per-language quality within 14 days; runbook and quality alerts within 30, each with its proof.

Rasael's rule in the lab: a missing item with impact 5 blocks; other findings with risk 8 or more become dated conditions with a named proof. The relaunch review happens when the blocking item is met. Present it to Ruwaida as a path to launch, not a refusal.

The capstone

Your capstone is this review, on a real or supplied service, with measured evidence

  • A peer's service, or the supplied Athar v2.7 release pack (labs/capstone/)
  • Objectives, capacity, degradation, an incident drill, release integrity, a decision
  • A public GitHub repository; a 10-minute defence with 5 minutes of panel questions
  • During the questions, the panel injects a fault and you diagnose it live

AI-full in the capstone: assistants are allowed for the work, which is then defended live. Ask each participant to name their service and the first three checklist items they will test before leaving.

Checkpoint

Which launch decision?

A service has every item met except two partial ones: its canary gates on latency only, and its fallback was never tested under a provider failure. Both have likelihood 4 and impact 4, so each scores a risk of 8. What do you decide under Rasael's rule?

Do not launch until both are fixed
Launch with two dated conditions, each with the evidence that proves it
Launch without conditions
Ask the team to rerun their own checklist
Why. No missing item has impact 5, so nothing blocks; each gap becomes a condition with a date and a proof.

Answer: B.
